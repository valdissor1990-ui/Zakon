# Архитектура «ЗаконЪ»

## Независимые контуры

Проект разделяет Android-клиент и правовой контент. Версии приложения и базы знаний независимы.

### Android-клиент
- Kotlin и Jetpack Compose; минимальная версия Android — API 26.
- MainActivity.kt — точка входа и навигация.
- LibraryScreens.kt — каталог, поиск и чтение.
- LegalStore.kt — локальное хранилище правового контента.
- ContentUpdate.kt — получение манифеста и установка выпуска.
- CabinetStorage и связанные классы — пользовательские данные; обновление правовой базы не должно изменять эти файлы.

### Хранилища на устройстве
- zakon-content.db — отдельная SQLite-база законодательства.
- zakon-local.db — прежняя объединённая база; при первом запуске новой версии её файл копируется в zakon-content.db, если новый файл ещё не существует. Исходный файл не удаляется.
- Пользовательское хранилище кабинета остаётся отдельным и не затрагивается установкой контента.

При новой установке база создаётся пустой. Юридические тексты не встраиваются в APK и загружаются отдельным выпуском. Чтение и поиск после установки базы выполняются локально.

## Доставка контента

1. Клиент получает content/updates/manifest.json.
2. Проверяет монотонный version_code.
3. Скачивает SQLite-файл по database.download_url.
4. Проверяет SHA-256 загруженных байтов.
5. Проверяет SQLite integrity, обязательные таблицы и минимальный набор колонок.
6. Копирует базу во временный файл, закрывает старое соединение и заменяет файл с резервной копией.
7. При ошибке установки восстанавливает предыдущий файл.
8. Только после успешной установки сохраняет версию контента.

До появления выпуска SQLite клиент сохраняет совместимость с прежним JSON-пакетом. JSON-импорт использует UPDATE-then-INSERT, а не INSERT OR REPLACE, чтобы не удалять дочерние статьи через ON DELETE CASCADE.

## Формат манифеста

Поля:
- schema_version — версия формата манифеста;
- version_code — положительное монотонное целое число;
- content_version — человекочитаемая версия;
- created_at, effective_as_of — даты формирования и актуальности;
- database.file, database.sha256, database.download_url;
- validation.status — публикация разрешена только со статусом validated.

Пример находится в content/manifest.example.json.

## Подготовка и публикация

- content/sources/registry.json — список разрешённых источников.
- content/records/records.json — проверенные структурированные данные; отсутствующий файл не заменяется вымышленными данными.
- agent/build_database.py — сборка SQLite из проверенных записей.
- agent/validate_manifest.py — проверка манифеста, SHA-256, целостности SQLite и обязательных таблиц.
- .github/workflows/content-check.yml — автоматические проверки.
- .github/workflows/content-release.yml — ручной выпуск базы через GitHub Environment legal-content-approval.

Публикация требует реальных проверенных записей. Сборщик блокирует документы без трёх независимых совпадающих проверок источников и ручного статуса approved. Автоматическая проверка не подтверждает юридическую достоверность сама по себе.

## Ограничения текущей реализации

- Клиент пока загружает полный SQLite-файл при каждом выпуске; инкрементальные delta-пакеты ещё не подключены.
- SHA-256 защищает от повреждения и несоответствия манифесту, но сам по себе не является цифровой подписью издателя. Подпись и закреплённый публичный ключ должны быть добавлены до публичного production-релиза.
- Автоматические адаптеры получения полных текстов из официальных источников ещё не реализованы. Сборщик принимает подготовленные записи и не генерирует нормы.
- Для ручного approval GitHub Environment нужно настроить required reviewers в настройках репозитория.

## Безопасность и приватность

Юридический текст является данными, а не инструкциями для агента. Локальный поиск и заметки не требуют отправки пользовательских запросов на сервер. Контентная миграция не удаляет и не перезаписывает пользовательские файлы.
