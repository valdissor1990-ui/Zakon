# Настройка независимого выпуска правовой базы

Эта инструкция относится только к публикации правовой базы. APK и версия Android-приложения при таком выпуске не меняются.

## 1. Создать защищённую среду GitHub

Откройте [Settings → Environments](https://github.com/valdissor1990-ui/Zakon/settings/environments).

1. Нажмите **New environment**.
2. Название должно быть точно: `legal-content-approval`.
3. В разделе **Deployment protection rules** включите **Required reviewers**.
4. Добавьте хотя бы одного проверяющего, который будет сверять подготовленный пакет.
5. Если доступно, включите запрет самостоятельного подтверждения запуска его автором.
6. Сохраните настройки.

Workflow дополнительно проверяет через GitHub API, что у среды действительно есть хотя бы один обязательный проверяющий. Если защита не настроена, публикация остановится до подписи и создания релиза.

## 2. Добавить закрытый ключ подписи

Откройте [Settings → Secrets and variables → Actions](https://github.com/valdissor1990-ui/Zakon/settings/secrets/actions).

1. Нажмите **New repository secret**.
2. Имя: `LEGAL_CONTENT_SIGNING_PRIVATE_KEY`.
3. Вставьте содержимое приватного PEM-ключа, который соответствует открытому ключу `content/signing/public.pem`.
4. Сохраните.

**Не отправляйте приватный ключ в чат, не добавляйте его в Git и не помещайте в APK.** В репозитории и приложении должен находиться только открытый ключ. Workflow подписывает манифест закрытым ключом и тут же проверяет подпись открытым ключом.

Если соответствующего приватного ключа нет, не создавайте секрет из случайного ключа: сначала потребуется контролируемая ротация пары ключей — обновить открытый ключ в репозитории и в Android-приложении, проверить сборку и только потом добавить новый закрытый ключ в GitHub Secrets.

## 3. Подготовить тексты законов

До первого выпуска в ветке `main` должны появиться:

- `content/records/records.json` — проверенные реквизиты документов, статьи, редакции, периоды действия, перекрёстные ссылки и история изменений;
- `content/evidence/<source-key>/...` — исходные файлы и метаданные захватов, созданные `agent/capture_sources.py`;
- минимум три совпадающих государственных источника из трёх разных информационных систем и минимум двух операторов для каждого документа.

Поисковая выдача, справочная страница и неофициальная правовая система не заменяют оригинал. Если редакция не подтверждена, запись не должна попадать в выпуск.

## 4. Запустить выпуск

После слияния проверенной ветки в `main`:

1. Откройте [GitHub Actions](https://github.com/valdissor1990-ui/Zakon/actions).
2. Выберите workflow **Build and publish legal content**.
3. Нажмите **Run workflow** на ветке `main`.
4. Введите версию, совпадающую с `release.version` в `records.json`.
5. Запустите workflow.

Сначала создаётся черновой SQLite-кандидат. Откройте артефакт `legal-content-candidate`, проверьте состав документов, количество статей, редакции, источники и контрольные суммы. Только после этого подтверждающий проверяющий одобряет job в среде `legal-content-approval`.

После одобрения workflow повторно проверит кандидат, подпишет манифест, проверит SQLite и подпись, создаст отдельный GitHub Release с полной базой и, если возможно, delta-пакетом, затем обновит манифест на `main`.

## 5. Проверить публикацию

После успешного завершения:

- в [Releases](https://github.com/valdissor1990-ui/Zakon/releases) должен появиться тег вида `content-X.Y.Z`;
- в релизе должны быть `manifest.json`, `manifest.sig`, `zakon-content.sqlite` и, при наличии, `zakon-content.delta.json`;
- файл `content/updates/manifest.json` в `main` должен иметь статус `validated`, положительный возрастающий `version_code` и ссылку на опубликованную базу.

Пока `records.json` отсутствует, запуск выпуска намеренно завершается ошибкой и ничего не публикует. Это защитное поведение, а не сбой приложения.
